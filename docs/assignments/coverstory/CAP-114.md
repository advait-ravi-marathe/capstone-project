## Acceptance plan

1. Three distinct 6/100 windows yield PENDING, PENDING, FIRING exactly once. Retrying a window key with unchanged values does not increment counts; changing the payload under the same key is rejected.
2. A healthy full-volume window resolves the active alert exactly once. Three 5/100 windows remain NORMAL because the comparison is strictly greater than 5%.
3. One error in two requests remains NORMAL; a later healthy 100-request window does not invent a prior firing or resolution.
4. The UI labels the synthetic Application case NEEDS_INFORMATION and lists only `policy_start_date` and `income_band` as requested field codes. Payment remains NOT_STARTED, dispatch false. Neither state is an alert-derived rejection, issuance, or active-cover decision.
5. Invalid counts and malformed window IDs are rejected; the same safe persisted state is returned after Spring restarts on the same disposable database.
