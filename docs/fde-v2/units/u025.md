# AIFDE-V2-U025: Bounded failure and recovery behavior

**Learner status: Not started.** Scheduled Days33–34 (60 minutes primary +60 minutes support/buffer). The supplied API maps one request to one bounded attempt; it does not retry automatically. This avoids duplicate model work and keeps cancellation/recovery behavior inspectable.

## Learn and do

Read FastAPI's official [handling errors](https://fastapi.tiangolo.com/tutorial/handling-errors/) and inspect the response paths in `ai/fde_v2/coverstory/api.py`. Distinguish invalid input (422), unavailable model/runtime (503), bounded generation timeout (504), busy local generation (429), and unexpected internal failure (502). Never include private exception text in the client response.

Run the failure-injection acceptance, which injects exactly one timeout then sends a valid request to the same app instance:

```sh
python3 -m unittest scripts.test_fde_v2_p1_closeout.FailureRecoveryAcceptance
python3 -m unittest ai.fde_v2.tests.test_continuation_api
```

These are explicitly simulated failures. On Day34, inspect the real loopback app with no model installed and record its actual 503 response; do not call this a model outage/recovery. If a verified real runtime exists later, observe one naturally bounded runtime-unavailable/recovery event without exhausting quotas or adding unbounded retries.

## Acceptance and evidence

Show a finite request deadline, one error response with no traceback disclosure, a subsequent valid request on the same app, and no duplicate automatic retry. Record whether evidence was simulated or an actual local runtime observation. The acceptance contract requires at least one actual runtime outage/recovery; test injection alone does not satisfy it, so U025 remains incomplete while that observation is unavailable.
