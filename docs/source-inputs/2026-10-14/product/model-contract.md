# Domain, API and persistence contracts

https://dwait-to-adwait.youtrack.cloud/issue/ECOS-19

## Context and modules
Browser React → Spring API → owning module → PostgreSQL. Catalog owns published versions. Shortlist references catalog versions. Application owns disclosures and accepted revisions. Payments owns attempts/reconciliation. Policy and Support own issued references and help cases. Use public module interfaces; no cross-module repository access. Payment adapter is a local mock Juspay interface; insurer decisions remain simulated. Public quote snapshots are sourced real evidence, classified separately from test fixtures. No runtime cache, broker or second database.

## Domain and invariants
CatalogVersion: DRAFT → PUBLISHED → RETIRED. Published version immutable; saved selections retain exact version. Every critical attribute carries value (nullable), evidenceStatus SYNTHETIC/VERIFIED/UNKNOWN, sourceRef and sourceAsOf. Unknown never means Included.
Shortlist: 1–3 unique catalog versions from one category. Anonymous save is device-local; authenticated save is owner-protected.
Application: AWAITING_PAYMENT → ONBOARDING → SUBMITTED → REVIEW → NEEDS_INFORMATION / OFFER_AVAILABLE → ACCEPTED / DECLINED → ISSUANCE_PENDING → ISSUED. Payment confirmation unlocks ONBOARDING exactly once. Corrections append a revision.
Offer: PROPOSED → ACCEPTED / DECLINED / EXPIRED; immutable terms hash, source version and expiry.
PaymentAttempt: CREATED → PENDING → SUCCEEDED / FAILED / UNKNOWN; reconciliation resolves UNKNOWN. Payment success never implies issuance.
Policy requires insurer issuance reference plus effective-cover evidence before active-cover language. SupportCase OPEN → WAITING_ON_USER / WAITING_ON_INSURER → RESOLVED; every event records source and actor.

## Examples and transactions
Valid synthetic shortlist {"category":"health","versionIds":["11111111-1111-4111-8111-111111111111"]}; empty versionIds rejected400 with no row.
Error {"code":"STALE_VERSION","message":"This draft changed. Reload before saving.","fieldErrors":[],"requestId":"demo-1","retryable":false}.
Mutating POSTs require Idempotency-Key16–128 chars, scoped actor+operation; seven-day sandbox retention proposed. Same key+hash replays stored result; mismatch409; in-flight duplicate returns bounded COMMAND_PENDING. Persist command result and mutation atomically.
Read Committed plus conditional version update and uniqueness. A/B readv4; A commitsv5; B update affects0 and returns412. Allowed one winner; forbidden silent overwrite. SQL serialization/deadlock retry at most2 with new transaction; never blind external retries.
Entity change + required outbox commit together. Provider calls outside transaction. Crash after commit before response recover by GET or same key. Outbox at-least-once with deduplication and aggregate-scoped order; no global exactly-once claim.

## Security, migration and evidence
Visitor only public catalog. Applicant only own objects. Support assigned-case minimum data; catalog editor cannot read proposals. Check authorization before serialization and at command boundary. Use standard Spring Security session/OIDC adapter when integration chosen; test principals confined to sandbox; CSRF/cookie/logout tested.
Synthetic fixtures only. No medical documents, secrets or answers in logs. Live PII retention/legal distribution/partner approval are launch blockers. Additive migration → backfill → verify → switch → later drop; restore before destructive change validates rowcounts/FKs/hashes.
Required tests Not run: fourth-item race; mixed categories; stale version; cross-owner IDs; duplicate/mismatched key; commit-before-timeout; duplicate/out-of-order callback; unknown serialization; migration restore.
Official guidance checked10-Sep-2026: https://www.postgresql.org/docs/current/transaction-iso.html ; https://docs.spring.io/spring-security/reference/servlet/authentication/session-management.html . Pin compatible actual runtime versions in first setup task.

## Repricing and adjustment contract
application_rating_revision(application_id,revision,initial_revision,scenario_hash,inputs,changed_fields,quote_id,confirmed_at), composite primary key. Preserve original values; extraction cannot overwrite a confirmed revision. PATCH draft with PIN/details triggers REQUOTE_REQUIRED when rating fields differ. POST /applications/{id}/requotes {ratingRevision} returns an exact supported quote or422 QUOTE_UNAVAILABLE; never estimate the payable total.
POST /applications/{id}/quote-acceptances {quoteId,ratingRevision,termsHash,totalMinor} binds the reviewed revision. In the same order-version transaction calculate netPaid and the balance against confirmed captures/refunds. Positive balance creates ADDITIONAL_PAYMENT, negative creates REFUND, zero creates no adjustment. Reserve pending amounts and serialize conflicting changes. Refund status is independently reconciled through the mock adapter. Original and revised quotes, inputs, payment events and refunds remain in history. A newer edit cancels an unstarted adjustment or waits for reconciliation if already dispatched; it cannot issue two refunds for the same balance.

No order side effect. Bind successful validation to buyer, exact snapshot and short validity. Proposed local validity5minutes; not insurer acceptance.

Confirmation transaction: validate mock event → deduplicate → update attempt/order → transition application AWAITING_PAYMENT to ONBOARDING → append timeline event. Duplicate callbacks leave one case. Revised offers occur after submission/review; adjustments cannot overwrite original payment evidence.

## Input controls and validation
Use labelled radio chips for short single-choice sets (product, smoking, payment frequency, Yes/No/Unsure), checkbox chips for genuine multi-choice sets, and native calendar date inputs with text/keyboard entry. Date-of-birth is a date-only value; reject future dates and calculate age using the insurer’s documented convention at the quote date. Calendar convenience does not replace server validation.
PIN input accepts exactly six ASCII digits starting1–9; the versioned supported master decides existence/coverage, not regex. Display verified city/locality and state beneath the field; loading, unsupported, ambiguous locality and unavailable lookup are distinct states. Tier is a separate versioned marketplace classification, never an inferred insurer pricing zone.
Names accept Unicode letters/marks, spaces, apostrophes and hyphens with a sensible1–120-character bound; reject control characters and blank-only input. A narrow Latin-only regex is unsuitable. Preserve the entered spelling and escape output. Exceptional legitimate names need an accessible correction/help path.
Normalize vehicle registration case and separators for matching while preserving display. Use separate format validators for standard state registrations and Bharat-series; route supported exceptions rather than treating one regex as proof of registration or ownership. Verify allowed state/RTO/series/year rules against an authoritative source before production. Server rules and clear field-linked errors are authoritative.


## Add-ons and bundles
Show sourced plan-specific optional and included benefits without preselecting optional paid cover. Each selection preserves product/UIN, variant, channel, source/version, eligibility, dependencies, exclusions, limits and selected-option IDs. Explain incompatible options. Compare base cover and selected configuration separately; show unknown incremental prices as Unknown. A source bundle total is not the sum of guessed rider prices. Changing an option requotes and requires review before payment or adjustment. No unsupported combination can proceed with a payable total.

## Onboarding and proposal boundary
Payment confirmation unlocks owned onboarding; it never sends a proposal to the insurer. Dispatch requires completed required fields/disclosures, confirmed extraction corrections, no unresolved questions, acceptance of the exact current proposal/quote/options revision, completed payment reconciliation and an explicit final submit action. Retain initial and edited details. Insurer submission is a separate durable state with an external reference.
Cancellation before any insurer dispatch is handled by the marketplace. Serialize cancellation with the dispatch claim; cancel or invalidate queued work atomically. An in-flight or unknown dispatch must be reconciled before treating the case as unsubmitted or granting a cancellation refund. After confirmed submission, show the insurer's verified contact route and applicable policy/source information; do not mark cancellation or refund complete from that alert.

## Refund destination and mock wallet
For a confirmed refundable amount, the buyer chooses original payment method or marketplace wallet. Nothing is preselected. Original-method refund shows a proposed 3–5 business-day estimate from provider acceptance, with a configured calendar/timezone and actual status; it is not a verified provider guarantee. A failed or unknown refund retains its reference and recovery action.
Mock wallet credit completes immediately at the successful internal ledger commit and is visible in the balance/history. Eligibility, available captured funds and ownership are checked first. A single unique adjustment allocation prevents crediting the wallet and refunding the same money to origin. Once an origin refund is pending, a route change requires confirmed cancellation of that attempt; uncertainty prevents duplicate credit. Wallet credit is labelled simulated, not a real stored-value facility.
Keep gateway settlement and application payment accounting separate. Application net settled = confirmed external captures + applied wallet debits − confirmed origin refunds − confirmed wallet credits attributed to that application. Pending allocations are reserved. Wallet available = confirmed credits − confirmed debits − active reservations, never negative. Do not double-count a wallet-funded portion as both external capture and wallet debit. Journal entries are immutable and reversals reference originals.
Real stored-value operation, cash-out/expiry/transfer rules, regulatory arrangement and verified provider refund timing are unresolved launch dependencies. The mock does not imply authorization to hold customer funds.

## Renewal and cancellation
Signed-in home and policy detail show expiry date from the verified policy record and a renew action before expiry. A renewal creates a linked application and fresh quote/configuration; never overwrite the existing policy or imply uninterrupted coverage before evidence. Reconfirm changed rating details, eligibility, disclosures, options and effective dates.
If no active mandate exists, show an in-app review-and-pay nudge with current amount/status and a secure route to quote review; the nudge cannot directly charge or skip login/consent. Active mandate, inactive/revoked mandate, unknown payment, already-paid renewal and expired policy have distinct states. Do not create or collect a real mandate. Expired/lapsed cases require the insurer's source-defined process and cannot promise backdated cover.
Before proposal submission, show cancellation confirmation, refundable-amount evidence, refund destination and reconciliation state. Afterwards, show an alert with the verified insurer contact route; retain the record for reference and help. Do not invent cancellation entitlement, amounts or insurer processing time.

Amounts are integer minor units with currency; browser amounts are never authoritative. All commands use safe errors {code,message,fieldErrors,correlationId,retryable}. A synthetic refund request is {expectedVersion:3,destination:"MOCK_WALLET",acceptedRefundMinor:40000}; acceptedRefundMinor:-1 is rejected. No real payment credentials appear in examples.

A lost response is resolved through the same reference, not a new money operation.

Relational extensions: catalogue_option(plan_version_id,option_id,rule_version,source_id,definition), bundle_component(bundle_version_id,option_id,required), configuration_snapshot(id,quote_id,canonical_option_ids,configuration_hash), adjustment_allocation(id,application_id,accepted_revision,amount_minor,destination,state,version), wallet_account(owner_id,currency,version), wallet_entry(id,account_id,allocation_id,order_id,direction,amount_minor,created_at,reversal_of), wallet_reservation(id,account_id,order_id,amount_minor,state,version), renewal_application(id,prior_policy_id,new_application_id,renewal_period_key), submission_record(application_id,reviewed_revision,state,external_ref,version).
Constraints: positive journal amounts, valid currencies, unique effect/reference keys, unique active renewal per policy/period, foreign keys, immutable posted entries, locked or optimistic-versioned balance updates and no overdraft. Keep customer identity and private rating answers out of public catalogue and logs. Index owner/time/id for journal reads and pending state/age for reconciliation; measure before adding indexes blindly.
Transactions: reserve/check/post wallet effects under one SQL transaction with allocation uniqueness; never assume a gateway refund is inside that transaction. Serialize cancellation and dispatch state claims on the application revision. Confirmed insurer submission has external evidence; UNKNOWN is neither unsubmitted nor completed. Observability: pending age, failed allocations, reconciliation mismatch, dispatch lag, rejected configuration count and privacy-safe correlation; no user IDs as metric labels.
Migration: additive tables and versioned contracts first, validate constraints/backfill before activation, keep old readers compatible, and disable new commands to roll back behavior while retaining journal/history. Test source withdrawal versus payment, dual-destination race, two wallet spends, cancel versus dispatch, duplicate renewal, cross-owner access and restore integrity on the real SQL engine.
