## Non-negotiable product invariants

1. **Source status:** Unknown is not Included. A hash proves integrity, not authority or applicability. Unsupported or incomplete price/scenario data yields QuoteUnavailable. Current illustrations and historical tariffs are never silently converted into payable quotes.
2. **Mock boundaries:** Payment and insurer behavior remain simulated unless a later separately authorized integration is verified. Payment success unlocks ONBOARDING once; it does not submit a proposal, issue a policy or establish coverage.
3. **Exact acceptance:** Every changed rating revision, options set, amount or terms requires explicit review and acceptance of the exact current tuple. All nonzero drift is visible. A 100-paise escalation threshold never grants permission to accept a changed amount silently.
4. **Submission:** Require complete disclosures, confirmed extracted-data corrections, no unresolved questions, current reviewed revision/quote/options/terms, reconciled payment and explicit submit. Use durable SUBMISSION_PENDING until a confirmed dispatch reference exists. Do not equate an HTTP acknowledgement with insurer receipt or acceptance.
5. **Money:** Use integer INR minor units and immutable positive journal amounts plus explicit direction/reversal references. Application net settled is confirmed external captures + applied wallet debits − confirmed origin refunds − confirmed wallet credits attributed to that application. Wallet available is confirmed credits − confirmed debits − active reservations and cannot be negative. Never count a wallet-funded portion twice.
6. **Cancellation and dispatch:** Serialize pre-dispatch cancellation with dispatch claim. Unknown or in-flight dispatch requires reconciliation, not a claim of unsubmitted/refundable state. After confirmed dispatch, retain the record and verified insurer contact/cancellation route without pretending the external cancellation completed.
7. **Refund routes:** The user explicitly chooses ORIGIN or MOCK_WALLET, with no preselected route. One adjustment allocation cannot create both effects. A pending origin route can change only after confirmed cancellation; an unknown result blocks wallet credit. Wallet credit becomes confirmed only at journal commit. Provider timelines remain unverified design assumptions.
8. **Renewal and coverage:** Create a fresh linked application and quote, preserving the previous policy. A renewal nudge or mandate does not authorize charging. Coverage needs insurer issuance reference and effective evidence.
9. **Durable effects:** Retries/replay epochs are infrastructure attempts. They cannot mint another capture, refund, submission, issuance or renewal. Retain business-effect uniqueness beyond response-cache expiry; ambiguous external results are reconciled before retry.
10. **AI:** Source-grounded assistance may explain attributable facts and conflicts. It cannot invent eligibility/coverage/payable prices, cross ownership boundaries, execute submission/payment, or treat an exact excerpt as sufficient evidence for advice. Confirm extracted fields before workflow use.

## Consumer protection, journey resume and screen analytics

The user's new requirement adds encrypted consumer payloads, auditable transaction histories, UUID journey/homepage resume and click/page-load tracking. These augment the recovered domain tables. The existing ApplicationRevision composite key remains authoritative; journey references application_id plus application_revision and the exact quote rather than copying mutable answers.

Use owned journey projections and append-only server step events for resume, separate transaction-audit events linked to actual attempts/journal effects, and a minimal best-effort analytics table. UUIDs are identifiers, never authorization. Anonymous discovery/compare/device-local save remains available; private resumable drafts require login for this MVP. After login, validate imported selections before creating an owned journey. Homepage lists only the authenticated owner's currently valid resume actions.

Server business state, required audit and journey transitions commit atomically. Browser PAGE_VIEW/CONTROL_CLICK events are untrusted observations and cannot create paid/submitted/issued state. Use a versioned field/name/target allowlist, event IDs, bounded dedup/retry/size/rate behavior and configurable purpose/consent/retention. Exclude form values, health answers, contact details, raw URLs/query strings, credentials and payment details. Losing or blocking analytics does not block checkout or resume.

Consumer payloads use an instructor-supplied maintained authenticated-encryption adapter with versioned envelopes, independent data/wrapping keys, exact object/revision binding and access checks before decryption. No raw payment credentials or secret values belong in stored snapshots. KMS context, if later authorized, contains only non-sensitive constant labels. TLS and encrypted database volumes/backups require separate deployment verification because field encryption leaves indexes and metadata visible to authorized storage access.

The encryption adapter must exist before any private draft persistence, even when its behavior is taught later. Ephemeral in-memory teaching keys cannot prove cross-process recovery: record the actual authorized retained teaching-key mechanism or fail KEY_UNAVAILABLE without plaintext fallback. Test tampering, wrong owner, missing key, rotation, module-boundary bypass and restore compatibility. No live KMS setup, persistent access or security-setting change follows from these planning tasks.

Preserve initiated, pending, failed, unknown, reconciled and succeeded transaction observations and their references. A pending intent is persisted before a mock provider call; recording its definitive result and audit is atomic. A database rollback does not leave an imaginary audit row: retain the prior pending/unknown record for reconciliation. Corrections/reversals append evidence. Configurable retention applies by purpose; all transaction data does not mean secrets or indefinite storage.

## Frontend system design and system management

Frontend learning progresses through component/module boundaries, state ownership, server-versus-client truth, explicit data flow and typed API contracts, route/reload/UUID resume, accessibility, safe rendering, bounded caching/performance, failure recovery, observation and testing. TanStack React Query v5 owns server state and in-memory private caching; form and URL/router state remain separate. A SPA refresh validates the session and refetches current owned journey data with loading/error fallbacks; it does not presume SSR hydration. Use owner-scoped versioned keys, bounded read retries, cancellation, targeted mutation invalidation and complete account-switch cleanup. Do not persist consumer records, secrets or queued mutations in browser storage. Tailwind provides shared semantic design tokens and finite typed variants in reusable parameterized primitives/compositions; domain hooks remain outside shared UI. Inter with a tested system-ui fallback is the selected open-source font, superseding prior font proposals while retaining the clean, youthful, low-clutter design psychology. Match the actual installed framework versions during setup; no dependency or asset is assumed present. The early supplied shell exposes learner backend work; later tasks deepen specific UI seams instead of starting a separate application.

System management stays tied to this product: configuration/secrets, module wiring, CI and reproducible builds, deployment/rollback design, telemetry/SLOs/incidents, access control, encrypted backups/restore, measured capacity and cost. Each practical day produces a CoverStory feature, test, measurement or verifiable engineering artifact. Optional infrastructure experiments answer a specific product architecture question and remain removable; they are not detached toy tracks. Repository changes begin only after the full board adaptation is saved and verified.
